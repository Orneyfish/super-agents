---
name: write-eval
description: Turn a feature or any other piece of work (a document, research, an analysis, a design, a plan, an operations task) into a written requirements doc plus strict evals (and a mockup for UI features) that the user reviews BEFORE any work is built. Use when the user wants to add or change user-visible behaviour, or says "spec this", "write evals", "define done". Not for typo or one-line changes, and not for bug fixes (use fix-bug). For several features at once use write-tickets.
argument-hint: <feature-name> [low|medium|high]
allowed-tools: Bash(super-agents *)
---

Evals are the fixed tests that decide whether work is done. Write them before building, make them strict enough that lazy work fails, and get the user to approve them. Do not write feature code or the deliverable in this skill.

Feature name = first word of "$ARGUMENTS" in kebab-case. Directory = `specs/<feature>/` (write-tickets passes a ticket directory instead).

1. **Kind and deliverable.** Decide what kind of work this is: `code`, `document`, `research`, `analysis`, `design`, `plan` or `operations`. Ask the user when it is unclear; a missing `**Kind:**` line means `code`. Name the deliverable: the repo-relative path of the file or files the work produces (required for every kind except `code`; never under `specs/` and never a git-ignored path). Then run `super-agents template kinds.md` and read the section for this kind: it says what done means, which check patterns to use and what a reviewer looks for. Done when: you can state the kind and the deliverable path, and you have read that section.
2. **Settle open decisions.** List every decision the work depends on that the request does not settle. Ask the frontier in rounds: the questions whose prerequisites are already settled, at most four per round, through AskUserQuestion or plain text, each with a recommended answer worded so that "yes" accepts it. A question that depends on an open one waits for a later round. Look up facts in the project (files, docs, existing specs) instead of asking; ask only about decisions. Skip this step when nothing is undecided. If the project has a `GLOSSARY.md`, use its terms in the requirements; when the interview settles a new term, add it there (the name, one sentence, an Avoid list). `GLOSSARY.md` is the project's own and is not fingerprinted. Done when: no open decision is left, or you have recorded that none existed.
3. **Requirements.** If `RD.md` is missing, draft it from the conversation using the template printed by `super-agents template RD.md`: summary, user stories, `FR-n` functional requirements (each one observable behaviour, testable on its own; names that other work relies on written out in full), `NFR-n`, the files or parts this work **touches**, what it **must not touch**, every **decision** made (each answer from step 2 goes under Decisions), **out of scope**, `UI: yes|no`, and the `**Kind:**` and `**Deliverable:**` lines (for `code`, delete the Deliverable line instead of leaving its TODO; otherwise the line holds only repo-relative paths, comma-separated, with no other text on it). Status starts `draft`. If `RD.md` exists, tighten it; never silently drop a requirement. If its `**Status:**` is not `draft`, the user already approved it and any edit fails the done-gate: say so and ask first; on yes run `super-agents board set <dir> draft`, then edit. Done when: `RD.md` has no TODO and every requirement can be observed.
4. **Risk.** Use the second argument if given, otherwise run the `super-agents:classify-risk` skill on the work. It sets the `**Risk:**` line in `RD.md`. Done when: `RD.md` has a `**Risk:**` line.
5. **Evals.** Create `evals.md` from the template printed by `super-agents template evals.md` and fill it in: a Setup section, one `## E<n>` block per check, and the Definition of done. Take the check patterns from the kind's section in `kinds.md`. Strictness follows risk, read as "what happens to whoever relies on this if it is wrong":
   - low: a happy-path eval per requirement, plus one failure-mode eval for the riskiest one. For non-code work: one check per requirement.
   - medium: per requirement a happy path and at least one error or edge case (empty, invalid, duplicate, retry, state after reload). For non-code work: someone is misled or redoes work, so add an error or edge case per requirement.
   - high: all of medium, plus abuse and safety evals: another user cannot read or change this data, no double-charge or lost write on retry, a failure midway leaves consistent state, hostile input, a rollback path. For non-code work: a decision about money, law, safety or people's data, or anything published or executed that cannot be taken back, so check every claim, not a sample, and add a rollback or correction path.
   Every eval needs a concrete `check` that someone who has never seen the work can run, a `pass when`, and a `fail when` naming what a stub or lazy work would show; `covers:` lists the `FR-`/`NFR-` ids it proves. If a stub could pass an eval, rewrite it. Example for FR-1 "the home page greets a visitor by the name they gave". Lazy, a hard-coded banner passes it: `check: open the home page`, `pass when: a greeting shows`. Strict:
   ```
   ## E1: greeting uses the given name
   - covers: FR-1
   - check: curl -s 'localhost:3100/?name=Ada' | grep -c 'Hello, Ada'; repeat with name=Bob and 'Hello, Bob'
   - pass when: both print 1
   - fail when: either prints 0, or the Bob page still says Ada (a fixed string)
   ```
   The pattern for every kind: two different inputs, and a `fail when` that names what the stub shows. Prefer automated checks (a test command, curl, a script); use browser steps only for UI, and then reference `mockup.html` at desktop and ~390px. When a check is judged by an agent (a reader test, a cold start), write the questions and expected answers into `evals.md` and require a quoted passage in the evidence. Taste (tone, look, persuasiveness) is not an eval unless you turn it into something observable. Setup: when the work has a running app, give it its own port, its own data directory and a test account, never real data; otherwise give a scratch directory and say never the real system, mailbox or source data. Done when: every requirement is covered by an eval and each eval has `check`, `pass when` and `fail when`.
6. **Mockup** (only if `UI: yes`; for kind `design` set `UI: no` and write no mockup, because the design is the deliverable and is built after approval). Write `mockup.html`: one self-contained static file, inline CSS, no build. Show every state the requirements imply (default, empty, loading, error, success, others) labelled, and the layout at desktop width and at ~390px. Reuse the project's existing look if it has one. It is a design reference for the tester to compare against, not a working app. Done when: `mockup.html` shows every state, or `UI` is `no` and you skipped it.
7. **Validate, then attack your own work.** Run `super-agents check-evals <dir>` and fix until it prints `OK`: each `FAIL:` line names one problem in `RD.md` or `evals.md`, so fix the file; if the same line survives two fixes, show it to the user. If the command cannot run at all (`super-agents` not found, or exit 3), say in the hand-over that the spec was not validated; never report an `OK` you did not see. Then reread every eval as an adversary and ask whether a stub could pass it; fix and rerun. Done when: `check-evals` prints `OK` and no eval can be passed by a stub.
8. **Hand over.** Status stays `draft`. Tell the user the file paths (open `mockup.html` with `xdg-open` on Linux or `open` on macOS, if present), the kind and deliverable you chose, the risk level you chose and why, and every decision you made on your own (assumptions, scope cuts, anything ambiguous). Say what to review: `RD.md`, `evals.md` and the mockup. Outcomes of a build go in `results.md`; these two files are not edited while building. Done when: your reply names the files, the kind, the risk and every decision.
9. **Stop.** Build nothing. If the user asks for changes, edit, rerun the check, stay `draft`. When the user explicitly approves, run `super-agents board set <dir> ready` and tell them to run `/super-agents:review-loop <feature>`. Done when: no deliverable or feature code exists and the status is still `draft`, or the user approved and the board is `ready`.
